# Changelog

Newest first. Each entry is dated by when it landed.

## 2026-11-01: packport 0.3.0, reading everything ConvertAll used 7-Zip for, with compiled decoders

- **Added:** one way to read every format packport knows. `packport.open(src)` takes a path, a list of volumes, bytes or a binary file, works out the format from the content (never the name), and returns an `Archive` whose `members` list what's inside and whose `files()` hands over each file's data in archive order, so solid archives are unpacked once. `packport.extract(src, folder)` unpacks any of them with `extract_cpio`'s safety rules, plus `on_rename`. `packport.detect(src)` names the format. Encrypted data raises the new `packport.EncryptedError`. `read_rar`, `read_cpio` and `extract_cpio` work as before.
- **Added:** reading compressed RAR: RAR 5 (with its filters, solid archives, volumes and BLAKE2sp checksums) and RAR 2.9 to 4.x (LZ, PPMd and RAR's standard filters, solid archives, volumes), self-extracting RAR files, and `.partN.rar` or `.rar/.r00` sets opened from any volume. On libarchive's 23 RAR test archives (41 volume files) that 7-Zip reads, packport gives the same bytes for every file; it differs only where it means to (it leaves symbolic links out). Speed: 3.7 MB/s for RAR 4 LZ and 7.1 MB/s for RAR 5.
- **Added:** reading 7z with every coder and filter 7-Zip writes: LZMA, LZMA2, PPMd, BZip2, Deflate, Deflate64, Zstandard, BCJ, BCJ2, ARM, ARM64, ARMT, PowerPC, SPARC, IA64, RISC-V and Delta. The 10 test archives 7-Zip wrote and all 58 of libarchive's 7z test archives that 7-Zip reads come out byte-identical (apart from one symbolic link). Encrypted folders and headers raise `EncryptedError`, and the members inside an encrypted folder are marked `encrypted`.
- **Added:** reading ZIP, for what Python's `zipfile` can't open: Deflate64, bzip2, LZMA, xz, Zstandard, PPMd (variant I), and PKZIP 1's Shrink and Implode members, ZIP64, self-extracting archives and archives with data in front, and damaged archives whose central directory is gone (packport then reads the local headers in order, as 7-Zip does). The 5 test archives 7-Zip wrote, all 45 of libarchive's ZIP test archives that 7-Zip reads, and Apache Commons Compress's 4 Shrink and Implode archives give the same files as 7-Zip, apart from symbolic links and names in old code pages (packport reads those in the DOS code page, as `zipfile` does). PPMd's "cut off" mode and big Shrink streams (codes widening to 13 bits, the table cleared 5 times), which 7-Zip reads but doesn't write, are tested on archives written by test-only encoders that 7-Zip extracts exactly. Encrypted members raise `EncryptedError`; Reduce, DCL Implode, JPEG and WavPack members get an error that names the method.
- **Added:** reading ISO 9660 disc images with Joliet, Rock Ridge (long names, permissions, times, symbolic links, continuation areas, folders moved to `rr_moved` put back where they belong), zisofs compression, files over 4 GB in several extents, and El Torito boot images (listed as `[BOOT]/Boot-1.44M.img` and so on, as 7-Zip names them). Of libarchive's 25 ISO test images, 21 give the same files as 7-Zip or, where 7-Zip doesn't read Rock Ridge or zisofs, as libarchive; the other 4 are hostile images that only raise `PackportError` (libarchive 3.8.9 itself loops forever on one and crashes on another). Where 7-Zip shows the 64-character Joliet names, packport keeps Rock Ridge's full names: on one test image 7-Zip cuts three names to the same one and writes a single file, packport writes all three.
- **Added:** reading UDF disc images, revisions 1.02 to 2.60 (physical, sparable and metadata partitions; short, long and inline allocation; the backup anchors when the first one is gone). A disc with UDF and ISO 9660 both is read through whichever lists more, UDF on a tie, so Windows install discs, which keep everything in UDF, come out whole; when the UDF side is damaged, the ISO 9660 side is read. UDF 1.02, 1.50, 2.00, 2.01 and 2.50 images written by Windows' own IMAPI2, and a bridge disc, give the same files as 7-Zip. Virtual partitions (multisession CD-R) are refused with a clear message.
- **Added:** reading disk images and the file systems on them. Containers: VHD (fixed, dynamic and differencing, read through the parent next to it), VHDX (the same three), VMDK (monolithic sparse, stream-optimized, and descriptor files with flat or sparse extents), QCOW2 (zlib and Zstandard clusters, backing files), VDI, DMG (raw, zlib, bzip2, ADC and LZMA chunks) and raw images. Partition tables: MBR (with extended partitions), GPT and the Apple Partition Map; one file system gives its files, several give a folder each (`1 NTFS`, `2 FAT32`), and a partition packport can't read comes out as a raw `.img`. File systems: FAT12, FAT16 and FAT32 with long names; NTFS (fragmented MFT, attribute lists, sparse files, LZNT1 and WOF compression; system files and alternate streams left out; EFS-encrypted files refused); ext2, ext3 and ext4 (extents, block maps, inline data; encrypted folders refused); HFS+ and HFSX (hard links, zlib-compressed files); APFS (encrypted volumes refused). BitLocker (To Go too), LUKS, LVM, encrypted DMGs and sparse images are refused with a message that names them. All 18 of dfvfs's test images packport reads give the same files as 7-Zip (apart from links and the system files 7-Zip lists), including differencing VHD and VHDX over their parents; NTFS's LZNT1 decoder unpacks what Windows' own compressor writes.
- **Added:** reading squashfs 4.0 (gzip, xz, lzma, LZ4 and Zstandard; fragments, holes, extended inodes, long folders). go-diskfs's mksquashfs images give the same files as 7-Zip and as the checksums made with them; gzip, xz and zstd images from a test-only writer give the same files as 7-Zip, and LZ4 ones (which 7-Zip doesn't read) the bytes the lz4 library packed. LZO images are refused with a clear message.
- **Added:** reading LZH/LHA (header levels 0 to 3; -lh0-, -lz4-, -lh4- to -lh7-, folders) and ARJ (methods 0 to 4), self-extracting ones included, with every file's CRC checked. All 11 of libarchive's LZH test archives that 7-Zip reads give the same bytes; Shift_JIS and UTF-16 names come out as they were meant, where 7-Zip shows them in the DOS code page or as underscores, and level 3 headers, which 7-Zip doesn't read, work too. Big LZH (-lh5- to -lh7-) and compressed ARJ (methods 1 and 4) archives, which nothing on hand writes, are tested on archives from test-only encoders that 7-Zip extracts exactly; Apache Commons Compress's two stored ARJ archives match 7-Zip. Garbled ARJ members raise `EncryptedError`; -lh1-, -lzs- and -lz5- get an error that names the method.
- **Added:** reading CAB (stored, MSZIP, LZX, cabinet sets), WIM (XPRESS and LZX), NSIS installers (zlib, bzip2 and LZMA, solid or not), ar and deb, RPM, xar and macOS `.pkg` (with the Payload unpacked), old binary and odc CPIO, and `.001` or `aa`, `ab`, ... split files. NSIS: all 653 files of the Ghostscript 10.08 installer match 7-Zip byte for byte (2.8 s, 7-Zip 1.9 s). CAB: every cabinet Windows' `makecab` writes (stored, MSZIP, LZX 15 to 21, a 4-cabinet set) matches 7-Zip.
- **Added:** writing uncompressed WIM (`write_wim`, and `.wim` in `pack` and on the command line), which 7-Zip reads back, and odc CPIO (`CpioWriter(out, fmt="odc")`).
- **Added:** `packport --list ARCHIVE` and `packport --extract ARCHIVE FOLDER` on the command line, for every format packport reads.
- **Added:** packport-native 0.3.0, packport's slow decoders again in Rust, as an optional package (`native/` in this repository; wheels for Windows, Linux and macOS on the release, one per platform for Python 3.10 and later). packport uses it when it's installed and gives the same bytes either way; without it nothing changes. It has LZX, RAR 2.9 to 5 (LZ, PPMd, filters), 7z's PPMd and BCJ2, ZIP's PPMd, Deflate64, XPRESS, LZH and ARJ, LZNT1, ADC, LZ4 and the checksums. `packport.accelerated()` says whether it's in use, and `PACKPORT_PURE=1` turns it off. Against packport's Python decoders: ZIP PPMd 96 times as fast, 7z PPMd 86, Deflate64 54 to 66, LZH 56, CAB LZX 46, RAR 4 9, BCJ2 3. Against 7-Zip 24.09 on the README's 18 archives: faster on 9 (squashfs 4.0 and 6.8 times, 7z folders 3.9, Deflate64 1.2 and 1.6, a stored CBR 1.4, MSZIP CAB and LZH 1.3, RAR 4 1.1), the same on 2 (UDF, WIM), and slower on 7: a bzip2 ZIP 1.2 times as long, one long LZMA2 stream 1.3, 7z PPMd 1.4, ZIP PPMd 1.5, BCJ2 1.7, CAB LZX 2.1 and the Ghostscript NSIS installer 2.3. The LZMA rows (one long stream, BCJ2, NSIS) are held back by Python's liblzma, which decodes the streams on its own more slowly than 7-Zip does the whole job (BCJ2's main stream: 0.71 s in liblzma, 0.42 s for 7-Zip to unpack the archive).
- **Added:** decoding on several cores at once, in archive order: 7z folders, WIM chunks, squashfs blocks and the files of a non-solid RAR archive. `PACKPORT_THREADS` sets the count (by default one less than the cores, at most 8; 1 turns it off). A 7z of 32 LZMA2 folders unpacks in 0.21 s, where 7-Zip takes 0.82 s.
- **Changed:** every file is unpacked a piece at a time and never held whole, in every format. Before, RAR, 7z (other than LZMA), CAB, NSIS, LZH, ARJ and ZIP's Deflate64, PPMd, Shrink and Implode members were decoded whole into memory, so a file of several GB in a RAR failed as "damaged" and Cancel had to wait for the end of a file. A 64 MB file took between 64 and 194 MB of memory before; now RAR 4 takes 5.1 MB, RAR 5 4.1 MB, 7z 2.4 MB stored and 6.0 MB with LZMA2, ZIP 2.1 MB, CAB 1.3 MB, WIM 2.1 MB, and a 48 MB solid NSIS installer 8 to 15 MB. A 5 GB file in a RAR now unpacks in under 64 MB.
- **Fixed (security):** a VHD, VHDX, VMDK or QCOW2 image could name its parent, extent or backing file with an absolute path, another drive, a network share (`\\server\share`) or `..`, and packport opened it: a FLAT extent could read any file as disk bytes, and a share name reached out over the network. Those names are now refused before anything is looked up; only files in the image's own folder are used, and the error says which file is needed.
- **Fixed (security):** a small 7z, ZIP or RAR file could ask for a PPMd model of up to 4 GB. Models over 2 GB, more than 7-Zip or WinRAR ever writes, are refused with a message that says so, and the model of a RAR file is freed before the next one is made.
- **Fixed (security):** RAR 2.9 to 4 filters with a start past the dictionary window or a length over RAR's 256 KB VM memory are refused as damage. Found by the new fuzz test, as were 113 cases where a damaged RAR ran packport out of memory.
- **Fixed:** WIM files are checked against the SHA-1 their header gives, as 7-Zip does; a damaged one raises `PackportError` instead of giving wrong bytes.
- **Fixed:** reading an empty 7z archive raised `AttributeError`.
- **Faster:** looking for an NSIS installer inside an exe that isn't one read 16 bytes at every 512-byte step through its first 64 MB; it now reads from the end of the exe's last section, 1 MB at a time (on a 100 MB exe, 131,109 reads in 62 ms before, 102 reads in 47 ms after). A WIM file shared by several names is decoded once, DMG reads whole chunks instead of 512-byte sectors (8.0 ms to 5.0 ms on the test image), and `extract` makes each folder once.
- **Fixed:** a ZIP whose central directory is gone is read from its local headers, and a Deflate member there whose sizes come after its data was checked against a CRC worked out from the data itself, so damaged data passed as good. It's now checked against the CRC stored after the data. Found by reading 39,400 damaged copies of the test archives with packport and with 7-Zip and comparing (see the README).
- **Fixed:** a VHDX whose first region table is damaged is read through the second copy (the format keeps two, each with a CRC-32C), as 7-Zip does; packport refused it.
- **Fixed:** the parent, extent and backing files a disk image opens (a differencing VHD or VHDX's parent, a VMDK's extents) were only closed when Python got round to it; on Windows that kept them locked. They're closed with the archive now. A damaged NSIS installer could also leave its temporary file open.
- **Changed:** reading from the same archive on several threads is safe: the parallel decoding and the new decoding ahead both read through it.
- **Changed (development):** any warning fails a test (`filterwarnings = error`); it found the two file-handle leaks above. The fuzz test records a panic in packport-native or a crashed worker process as a finding instead of stopping. The `dev` extra installs `backports.zstd` on Python before 3.14, so the Zstandard tests run, and `lz4`, so the LZ4 squashfs test runs; CI runs the suite on Python 3.11 too (3.10, 3.11 and 3.13; the README says 3.10 and later).
- **Faster:** PPMd in packport-native: 7z's 33% faster (1.81 s to 1.21 s on 6.3 MB of text, decoding only) and ZIP's 15% (1.57 s to 1.33 s): no memory allocated per symbol, and ZIP's range decoder in 32-bit arithmetic as 7-Zip's is. A big 7z or cabinet folder is decoded in a thread of its own while its files are written, and BCJ2's four streams side by side (4 to 5% on the benchmark's LZMA2 and BCJ2 archives); a cabinet's blocks are read and handed on a megabyte at a time instead of 32 KB at a time. Native and Python decoders still give the same bytes on all 2,915 cases.
- **Known slow without packport-native:** packport's Python decoders unpack PPMd at about 0.1 MB/s and LZX at about 3.6 MB/s, far slower than 7-Zip; big archives in those methods take minutes.
- **Tests:** 660: 649 passed and 11 skipped with packport-native, 646 passed and 14 skipped without it (193 passed, 3 skipped at 0.2.1), with any warning failing a test; the 4 big-file tests run with `PACKPORT_SLOW=1`, and the 6 that need zstd and lz4 skip where those optional modules aren't installed. packport-native also has 10 Rust tests (`cargo test`), and its decoders give the same result as the Python ones on every test archive and on 2 damaged copies of each (ZIP's PPMd: 804 cases). The fuzz test's deep pass (`python tests/fuzz_readers.py 200`) read 53,000 damaged copies of the 265 test archives: the first run found 113 that ran a RAR reader out of memory (fixed, above); in the last, nothing but `PackportError` came out of any copy and none ran out of memory; the only cases listed were 13 damaged ZIP PPMd copies that the Python decoder took 5 to 9 s over on a busy machine. Rerun on their own, they take 1.4 to 3.1 s (the intact archive takes 3.2 s), packport-native refuses each in about 0.1 s, and 7-Zip calls every one of them damaged too ("Data Error"); the test now compares a damaged copy's time with the intact archive's. Native and Python decoders give the same result on 2,915 cases (every test archive and 10 damaged copies of each). They include 170 of libarchive's test archives (under its BSD license, `tests/data/libarchive`), 6 of Apache Commons Compress's (under the Apache License 2.0, `tests/data/commons-compress`), one of go-diskfs's (MIT, `tests/data/go-diskfs`) and 23 of dfvfs's disk images (Apache License 2.0, `tests/data/dfvfs`, rebuilt by `tests/data/make_dfvfs_fixtures.py`), checked against 7-Zip's output, and 34 archives and images in `tests/data/made` (15 from 7-Zip, 11 from test-only writers, 2 El Torito images from libarchive's ISO writer and 6 UDF images from Windows' IMAPI2; 7-Zip reads back every one it can), rebuilt by `tests/data/make_fixtures.py`.

## 2026-10-30: packport 0.2.1, safer CPIO extraction and .Z decoding

- **Fixed (security):** on Windows, `extract_cpio` could write an alternate data stream from a name like `dir/a.txt:hidden`, because it only checked the first part of a name for `:`. It now makes every part of a name safe the way 7-Zip does: characters Windows doesn't allow become `_` (so `a.txt:hidden` becomes `a.txt_hidden`), a trailing dot or space becomes `_`, and device names such as `CON` or `nul.txt` get a `_` in front.
- **Fixed (security):** a small archive could fill the disk through hard links, because each link wrote another full copy of its file. The new `max_size` caps the bytes written, counting every copy.
- **Changed:** `extract_cpio` never overwrites a file. A name that's already taken, whether written twice in the archive, already in the folder, or differing only in case on Windows, is saved as `name (1).ext`.
- **Added:** `on_skip(name)` hears about each member that's left out (names that would climb out of the folder, links, device files).
- **Fixed (security):** an archive with the same name many times made `extract_cpio` retry every earlier ` (n)` name for each copy, which grows with the square of the count. It now remembers where each name got to: 300 copies of one name took 45,150 file-open attempts before and 300 now.
- **Fixed (security):** a CPIO header could claim a name of up to 4 GiB, and packport tried to read it all. Names longer than 64 KiB are now refused before they're read, by `read_cpio` and `extract_cpio` alike. `CpioWriter` refuses to write them too.
- **Added:** `extract_cpio(..., max_files=1_000_000)` caps the number of members, so an archive of millions of empty files can't flood a folder. `None` turns it off.
- **Fixed:** a CPIO archive with a file and a folder of the same name (a file `a`, then `a/b.txt`, or a file `d`, then a folder `d`) stopped `extract_cpio` with an `OSError`. The folder, or the file inside it, is now skipped and reported to `on_skip`; a file whose name is taken by a folder is saved as `name (1)`.
- **Fixed:** top-level names with a colon were skipped even though the docs said they're renamed. Now only a name starting with a bare drive (`C:/...`) is skipped; on Windows `a:b` becomes `a_b` and `D:rel.txt` becomes `D_rel.txt`, and elsewhere they're kept as they are.
- **Fixed:** hard links whose data comes with the first link (as GNU cpio writes them) came out empty, apart from the first. Every link now gets the data, whichever one carries it, and links are only created once the data is known, so a `max_size` stop leaves no empty placeholders behind.
- **Fixed (security):** the `.Z` decoder kept each dictionary entry as a whole string, so a 19 KB hostile stream made it hold 73 MB at once (and about 2 GB at the format's limit). It now keeps (prefix code, byte) pairs, like the original `compress`, with whole strings only up to 16 MB for speed: the same stream peaks at 18 MB, and normal files decode within 3% of the old speed (text 15.5 MB/s before, 15.1 MB/s after).
- **Changed:** `decompress()` now caps its output at 1 GiB by default (`max_size=None` turns the cap off). `ZDecompressor`, which hands output back a piece at a time, still has no cap unless you give one.
- **Fixed:** `pack("out.Z", ...)` took only a path or bytes. A mapping like `{"a.txt": data}` made it open a file called `a.txt` from the current folder instead, and an `Entry`, a `(name, data)` pair, a `bytearray` or a `memoryview` raised the wrong error. It now takes everything the other formats take, and a folder or several files raise "`.Z` holds a single file".
- **Fixed:** `read_rar` returned the files before the cut when an archive was cut short exactly between two files. A RAR archive without its end-of-archive block now raises `PackportError` ("cut short"), as a CPIO archive without `TRAILER!!!` already did.
- **Fixed:** modification times a format can't hold (before 1970, far in the future, infinite or NaN) made `write_rar`, `write_cpio` and `write_tar_z` fail with `OSError`, `OverflowError` or `ValueError`. They're now clamped to the format's range; `.tar.Z` no longer stores negative times.
- **Fixed:** on Windows, files with the read-only attribute weren't flagged read-only in RAR (or given mode `0o444` in CPIO and `.tar.Z`). They are now.
- **Docs:** the README gives the real size (about 58 KB of source, a 28 KB wheel, about 160 KB installed), and says that `read_rar` and `read_cpio` return names as stored, which aren't safe to use as paths.
- **Added:** tests for all of the above: 29 new ones, each building its hostile archive in code; 28 of them failed before these fixes (the one exception, `pack` with plain bytes, guards what already worked). The suite is now 193 passed, 3 skipped (164 before).

## 2026-10-26: Tests pass on Python 3.10.11 (after the 0.2.0 tag)

- **Fixed (tests only):** the `.tar.Z` round-trip test used `tarfile`'s extraction filter, which Python 3.10.11 (the last 3.10 with a Windows installer) doesn't have. It now uses the filter only where it exists. Found by the new GitHub Actions run on Python 3.10.

## 2026-10-26: packport 0.2.0, streaming CPIO extraction

- **Added:** `extract_cpio(archive, folder)` unpacks a CPIO archive straight to disk in 1 MB pieces, so archives larger than memory work. It never writes outside the folder: leading slashes are dropped (as bsdtar does), names that would still climb out or name a drive are skipped, and so are symbolic links and device files. Files keep their modification times, and hard links each get the file's data.
- **Changed:** `read_cpio` reads the archive as it goes instead of loading the whole file first, and both accept an open binary file as well as bytes or a path.
- **Added:** tests for extraction: round trips, streaming, hostile names, links, hard links and damaged archives.
- **Added:** GitHub Actions run the tests (Python 3.10 and 3.13 on Windows, with 7-Zip) and `ruff check` on every push and pull request, plus `CONTRIBUTING.md` and `SECURITY.md`. `ruff` is in the `dev` extra.

## 2026-10-26: packport 0.1.0, first release

- **Writes RAR 4** (`.rar`, `.cbr`) with stored entries, written from RARLAB's published format description:
  - folders, including empty ones;
  - Unicode names in RAR's Unicode name encoding;
  - files over 4 GiB, with the 64-bit size fields;
  - modification times, CRC32s and the read-only flag;
  - streaming, so files larger than memory work.
- **Writes Unix compress** (`.Z`): 9 to 16-bit LZW in block mode. The output matches libarchive's compress writer byte for byte, and gzip, 7-Zip and libarchive read it. Also `.tar.Z`.
- **Writes CPIO newc** (`.cpio`): files, folders, permissions and modification times.
- **Reads** stored RAR 4, `.Z` and CPIO newc, for round trips without other tools. Damaged archives raise `PackportError`; `.Z` output can be capped with `max_size`.
- **Command line:** `packport SOURCES... OUT`, with the format taken from OUT's extension.
- **Tested** byte for byte against RARLAB's own unrar (bundled with calibre), 7-Zip, libarchive (Windows' `tar.exe`) and gzip. The tests use Unicode names, empty folders and files, sparse files of 3 GiB and over 4 GiB, corrupted archives and random trees. They pass on Python 3.10, 3.11 and 3.13 and in a PyInstaller build.
